## Status values

- `not_started` — no implementation work has begun.
- `in_progress` — an agent owns the milestone and is actively working it.
- `blocked` — progress requires a named external decision, permission, or state
  change.
- `complete` — every exit criterion is satisfied and linked evidence exists.

Normally only one milestone is `in_progress`. If parallel milestones are active,
their owners and non-overlapping file scopes must be recorded in Current Work.

## Current work

M10 security hardening is in progress, owned by Codex `/root`.

- The approved program preserves elevated applications, saved Startup Sequence
  order, existing profiles, manual online update checks, and the existing
  FormationLapCore and ProcessRuntime public interfaces.
- The first slice is complete: one verified Windows Process handle is held
  through each action, exact monitored paths exclude same-name decoys, Test Game
  Launch learns a sanitized profile-local path, and filename-only matches cannot
  become Session-owned.
- The second slice is complete: ProfileLibrary retains trusted source paths,
  canonical UUID IDs must match filenames, and invalid legacy identities are
  repaired into new UUID-backed profiles while preserving the original as a
  recoverable backup.
- The third slice is complete: the main and helper independently authenticate
  the exact sibling pair, pipe-server and helper user/Session, protocol, nonce,
  and release identity. Unsigned previews install a Minisign manifest binding
  the final main/helper hashes, version, protocol, and release channel.
- The fourth slice is complete: Core executes elevated entries at their saved
  position, batches adjacent entries only, journals every stable identity before
  ownership acknowledgement, and the helper compensates for a missing
  acknowledgement by stopping the just-launched Process.
- The fifth slice is complete: only newly imported portable profiles enter
  `NeedsReview`; native approval requires the complete configuration
  confirmation and the exact elevated/custom-stop application IDs; missing
  paths or protected recipe changes keep or return the profile to quarantine;
  Dashboard and editor behavior expose and resolve that state without moving
  policy into React.
- The sixth slice is complete: it copies a non-conflicting roaming store through a
  validated temporary LocalAppData sibling before atomic activation, leaving
  roaming data untouched. It also replaces the generic HKCU Run value with an
  exact-owned `com.formationlap.desktop.StartWithWindows.v1` value and applies
  the same exact-ownership rule during legacy migration and uninstall.
- The seventh slice is complete: the native-owned UpdateCoordinator makes
  automatic checks opt-in for new users while preserving an explicit stored `true`,
  cancels and joins provider work before Session activation, excludes install
  overlap through native/core-owned activity leases, and constrains official
  update URLs, redirects, sizes, signatures, and verified staging before UAC
  installer launch.
- The eighth slice is complete: WinVerifyTrust plus approved signer
  certificate equality for signed Beta/Stable main-helper pairs and adds
  adversarial release qualification around signed/preview identity boundaries.
- All eight requested repository hardening slices are implemented. There is no
  active implementation file scope; native executable selection is available in
  the Racing Profile editor and first-run Manual Entry. M10 remains
  `in_progress` because a paid, separately authorized signed Beta and the
  Windows 10/11 release matrix are external qualification work.
- Local candidate commits `0bb2c75` and `c5e8faa`, plus the eight focused
  security-hardening commits, remain unpublished. No push, tag, workflow
  dispatch, signing operation, or GitHub release is authorized.
- Native Launch Quarantine now names each blocked executable, direct recipes
  derive working directory and process identity, and the recipe editor gives
  the executable path visual priority. There is no active implementation file
  scope.
- The native executable picker opens at the selected recipe executable's
  parent folder when that file exists, and otherwise keeps Windows' normal
  fallback. There is no active implementation file scope.
- Windows extended-length executable paths now render in their familiar form
  while canonical values remain available to native validation. There is no
  active implementation file scope.
- The Dashboard now preserves native launch-recovery messages and explains
  immediate startup exits. There is no active implementation file scope.
- A new Session keeps its Pending startup steps when a terminal Process snapshot
  from an earlier manual action is still in memory. There is no active
  implementation file scope.
- Not Responding now only reports an unresponsive visible top-level window;
  invisible internal windows are not user-visible evidence of a hung Process.
  There is no active implementation file scope.
- A requested elevated shutdown remains Stopping until the Process exits, so
  refresh cannot reissue its UAC request. There is no active implementation
  file scope.
- An explicitly confirmed Force stop remains available for a Stopping
  Session-owned Process while a Session is Closing, so a non-exiting elevated
  Process cannot block the remaining ordered cleanup.
- A successful explicit Force stop advances ordered Session cleanup immediately,
  rather than waiting for an unrelated Process refresh. There is no active
  implementation file scope.
- Session-owned same-executable descendants are traced inside the Windows
  ProcessRuntime. Their window state contributes to observation, Close Windows
  reaches every companion UI, and waiting/force stop retain the same stable
  identities. Applications without a companion keep the ordinary one-Process
  path. There is no active implementation file scope.
- Le Mans Ultimate now exposes only its documented SteamVR launch route in the
  Curated Catalog. Selecting the unsupported OpenXR mode is rejected before a
  Session starts instead of silently launching Steam option 3. There is no
  active implementation file scope.
- Dashboard lifecycle rows now use fixed Requirement, Status, and action
  tracks, so variable labels cannot shift one row out of alignment. Requirement
  text is centered within its pill. There is no active implementation file
  scope.

## Blockers

- The GitHub repository has an empty `release` environment. Signed v1 still
  requires its protection rules, a production Tauri updater key, and either
  approved SignPath Foundation integration or Microsoft Artifact Signing/Azure
  OIDC.
- Technical-preview candidate commit `0bb2c75` is local and requires explicit
  approval before it may be pushed. Creating/pushing its tag, dispatching the
  preview workflow, and publishing the prerelease remain separate external
  actions.
- A signed Beta must pass the Windows 10 22H2 and Windows 11 install, launch,
  update, uninstall, and accessibility matrix before a Stable v1 tag.
- Creating any preview, Beta, or Stable tag or GitHub release remains an
  explicit external publication action.

## How to update this ledger

When starting a milestone:

1. Change its Status to `in_progress`.
2. Set Owner and Started.
3. Replace Current Work with the exact slice and files being touched.
4. Append a Handoff log entry before yielding.

When completing a milestone:

1. Verify every exit criterion in `BUILD_PLAN.md`.
2. Link durable evidence in the milestone row or a dedicated evidence section.
3. Set Status to `complete` and add the completion date.
4. Clear Current Work and identify the next ready milestone.

When blocked:

1. Set Status to `blocked` only when the work truly cannot continue.
2. Record the exact missing permission, decision, dependency, or external state.
3. Name the smallest action that would unblock progress.
