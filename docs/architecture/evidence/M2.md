# M2 — Racing Profiles and transparent persistence evidence

Status: `in_progress`

## Slice 1 — Create and reopen one Racing Profile

Public test seam: FormationLapCore with a real temporary storage directory.

Observable behavior:

- `CreateProfile` accepts a Racing Profile name and exactly one Primary Sim
  name.
- FormationLapCore assigns a stable identifier.
- `snapshot()` lists the created Racing Profile.
- Reopening FormationLapCore from the same directory returns the same
  identifier, Racing Profile name, and Primary Sim name.

Persistence uses one human-readable JSON document per Racing Profile:

```json
{
  "schemaVersion": 1,
  "id": "<stable UUID>",
  "name": "Le Mans Ultimate",
  "primarySim": {
    "name": "Le Mans Ultimate"
  }
}
```

Creation writes and synchronizes a temporary file in the `profiles` directory,
then renames it to `<profile-id>.json`. Incomplete `.tmp` files are not treated
as Racing Profiles.

### Red

`created_racing_profile_survives_core_restart` initially failed to compile
because `FormationLapCore`, `AppCommand`, `CommandOutcome`, and
`ProfileSummary` did not exist at the approved public seam.

### Green

The same test passed after adding the minimal core and ProfileLibrary behavior:

```text
cargo test --manifest-path src-tauri/Cargo.toml --test racing_profiles \
  created_racing_profile_survives_core_restart

test created_racing_profile_survives_core_restart ... ok
```

## Slice 21 — Use an atomic Windows profile replacement

Public test seam: FormationLapCore with real temporary storage.

The earlier recovery protocol protected the last valid document after an
interrupted pair of renames, but a successful replacement still had a brief
interval with no live profile path. The green persistence suite allowed that
implementation detail to be safely refactored without changing the public
interface.

Profile edits, complete saves, and schema migrations now call Windows
`ReplaceFileW` with the flushed temporary document and the bounded backup path.
The OS swaps the live document and captures its previous contents as one atomic
filesystem operation. The existing recovery protocol still removes an orphaned
temporary document or restores a valid backup left by an older interrupted
write.

```text
cargo test --manifest-path src-tauri/Cargo.toml --test racing_profiles

Tests 12 passed
```

## Dependencies

- `serde_json 1.0.151` serializes the transparent local documents and adds no
  process, network, or privilege capability.
- `uuid 1.24.0` supplies version-four stable identifiers using local randomness
  and adds no process, filesystem, network, update, or privilege capability.
- Both versions were already present transitively in `Cargo.lock`; M2 records
  them as direct dependencies because the core now uses them directly.
- `windows-sys 0.61.2` exposes only the focused
  `Win32_Storage_FileSystem::ReplaceFileW` binding used by ProfileLibrary. It
  adds direct filesystem capability solely to make successful profile
  replacement atomic; it adds no process, network, update, or privilege
  capability.
